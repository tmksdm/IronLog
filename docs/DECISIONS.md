# Решения проекта

## 2026-09-03 — Локальные данные являются источником истины

- **Контекст:** Supabase используется как резервная копия и может быть недоступен без VPN; одноразовые cloud-delete запросы позволяли удалённым данным вернуться.
- **Решение:** все локальные операции работают без сети, cloud pull разрешён только для действительно пустой локальной базы, а удаления сначала записываются в SQLite-очередь `cloud_delete_queue`.
- **Причина:** потеря локальных тренировок недопустима; сетевой сбой не должен менять пользовательский результат.
- **Последствия:** очередь является внутренним состоянием синхронизации и не входит в пользовательский экспорт; cloud pull сначала обязан обработать её.

## 2026-09-03 — Native Android-проект генерируется при сборке

- **Контекст:** `android/` намеренно исключён из Git, из-за чего прежний `npm run build:android` падал на чистом checkout.
- **Решение:** хранить `@capacitor/android` в зависимостях и запускать `scripts/prepare-android.mjs`, который делает `cap add android` либо `cap sync android`.
- **Причина:** локальная команда и GitHub Actions должны использовать один воспроизводимый путь.
- **Последствия:** изменения нативной конфигурации нужно оформлять через Capacitor config или отдельно пересматривать решение о хранении `android/` в Git.

## 2026-09-03 — Тяжёлые экраны загружаются по маршрутам

- **Контекст:** единый production bundle был около 1,09 МБ и создавал предупреждение Vite.
- **Решение:** использовать `React.lazy` для экранов вне главной страницы и отдельные vendor chunks для React, Supabase и SQLite.
- **Причина:** основной сценарий запуска не должен ждать аналитику и другие редко открываемые экраны.
- **Последствия:** переход на ещё не загруженный экран кратко показывает общий `LoadingScreen`.

## 2026-09-04 — PWA-обновления активируются автоматически

- **Контекст:** обязательное подтверждение обновления внутри приложения создаёт тупик, если текущая оболочка уже не может отрисовать интерфейс или загрузить ленивый маршрут.
- **Решение:** новый service worker активируется после полной загрузки кэша и сам перезагружает все управляемые окна через `WindowClient.navigate`; клиентский `controllerchange` остаётся дополнительным механизмом. После перехода окон сохраняются текущий и один предыдущий кэш, более старые удаляются.
- **Причина:** возможность получить исправление не должна зависеть от работоспособности исправляемого интерфейса.
- **Последствия:** открытая PWA может автоматически перезагрузиться; это работает и при уже сломанном JavaScript старой страницы. Незавершённая силовая тренировка сохраняется в SQLite и восстанавливается штатным механизмом; один предыдущий кэш временно занимает дополнительное место.

## 2026-10-16 — Совместимость тестовых заглушек проверяется сборочными проверками

- **Контекст:** `npm run build:test` подменяет три модуля (`supabase.ts`, `sync.ts`, `SyncDiagnostics.tsx`) заглушками по списку `TEST_BUILD_MODULE_STUBS` в `vite.config.ts`. Подмена происходит в резолвере Vite и невидима для `tsc`, который всегда разрешает production-модули, поэтому заглушка могла отстать от интерфейса приложения и расхождение проявилось бы только в рантайме тестовой сборки. Ни типы, ни проверка артефакта этого не покрывали: типы дают лишь внутреннюю корректность файлов заглушек, а артефакт проверяется на утечку credentials и на факт подмены.
- **Решение:** совместимость проверяется тремя независимыми способами, каждый из которых подключён к штатным проверкам, а не к отдельному стенду.
  - `src/lib/cloudStubContract.ts` — типовой контракт, который проверяет каждый `tsc -b`, то есть все четыре сборки. Модуль `sync` и компонент диагностики сверяются строго (`typeof realSync = stubSync`); для компонента сравнивается используемая поверхность `() => ReactNode`, потому что возврат `null` законен для React и строгое сравнение выведенных типов давало бы ложную тревогу. Клиент Supabase сверяется узким контрактом в обе стороны: и production-клиент, и заглушка обязаны удовлетворять одной описанной поверхности, что ловит дрейф с обеих сторон. Негативные случаи (отсутствующий экспорт, суженный параметр, изменённый возврат, потерянная форма ответа, несуществующий член) записаны через `@ts-expect-error`: пока контракт отвергает такую форму, директива использована, а при ослаблении контракта она становится неиспользуемой и валит ту же самую сборку.
  - `scripts/ci/supabaseSurface.mjs` — структурный анализ фактически используемой поверхности клиента через компиляторный API TypeScript. Каждый путь члена разрешается по типу заглушки, а не по тексту: метод, которого в заглушке нет, и член, намеренно падающий в тестовой сборке (`from(): never`), запрещены вне подменяемых модулей. Список исключений читается из `TEST_BUILD_MODULE_STUBS` в `vite.config.ts` и потому не может разойтись с конфигурацией сборки. Цепочка принимается только тогда, когда она вызывается: способы обращения, которые анализатор не может довести до конца (деструктуризация клиента, передача его или его промежуточного объекта как значения, сохранение `const auth = supabase.auth`, ссылка на метод без вызова, локальный алиас, вычисляемый ключ), сообщаются как нарушение, а не пропускаются.
  - `src/lib/cloudStubBehaviour.test.ts` — поведенческий контракт: заглушки обязаны падать закрыто (никакой сессии, вход отклонён, `from` бросает), не делать сетевых запросов и не содержать ни SDK, ни production-credential.
- **Причина:** изоляция тестового стенда и сохранность данных важнее удобства. Расхождение интерфейса должно ломать штатную сборку или тесты, а не выясняться на телефоне при первой тестовой записи.
- **Последствия:** заглушки получили параметры, соответствующие production-сигнатурам, и `getSession` теперь сообщает `error: null`, как реальный клиент в варианте «нет сессии, нет ошибки». Строгая сверка типов SDK для клиента невозможна: `AuthError` объявляет `protected`-член, то есть типизирован номинально и не воспроизводится без SDK, поэтому поле `error` в контракте имеет тип `unknown`, а сам контракт описывает используемую поверхность; точность доменных типов обеспечивается тем, что код приложения компилируется против реальных модулей. Новое обращение к клиенту вне подменяемых модулей требует осознанного расширения контракта и заглушки, иначе `npm test` красный; ожидаемый список из четырёх путей в тесте анализатора образует такую же точку ревью. Поскольку `@types/node` не входит в `types` проекта, проверка исходников заглушек читает их через `import.meta.glob` (`?raw`) и не пишет на диск.

## 2026-10-16 — Проверка hostname выполняется до загрузки приложения

- **Контекст:** `HostGuard` принимал решение на рендере, но модули исполняются раньше рендера: entry статически импортировал `App`, а вместе с ним весь стек маршрутов, локальной базы, сторов и облака. В production-сборке `createClient` на верхнем уровне создавал клиент и запускал `initialize()` (`@supabase/auth-js`, конструктор `GoTrueClient`) до решения; в тестовой сборке облако было подменено, но свойства «до решения ничего не исполняется» не существовало ни как гарантии, ни как проверки. Измерено на артефакте: `index.html` объявлял `modulepreload` для `sqlite-vendor` и `supabase-vendor`, то есть браузер тянул SQLite и SDK ещё до проверки.
- **Решение:** решение о hostname перенесено на уровень входа и само приложение загружается только после разрешения.
  - `src/lib/entryGate.ts` — `resolveEntry` поверх существующего `decideHost` (политика не дублируется) с инъекцией загрузчика: на запрещённом адресе загрузчик не вызывается вовсе, ошибка импорта возвращается, а не выбрасывается.
  - `src/main.tsx` импортирует `App` только динамически и только при разрешённом адресе, импорты компонентов прямые (без бочки `components/ui`), ошибка загрузки чанка показывает собственный экран, поэтому бесконечной загрузки не бывает.
  - `HostGuard` остаётся вторым рубежом с теми же правилами, а `BlockedHostScreen` — единственным блокирующим экраном на оба слоя.
  - `scripts/ci/check-artifacts.mjs` проверяет статическое замыкание entry: разбирает импорты собранных чанков синтаксическим деревом (динамический `import(...)` и строки таблицы предзагрузки рёбрами не считаются), сверяет список импортов `src/main.tsx` с разрешённым, проверяет `modulepreload` и связывает чанки с исходными модулями через граф модулей. Пустое замыкание, неполный граф, отсутствующий entry или чужой модуль — отказ.
- **Причина:** гарантия должна быть свойством артефакта, а не намерением кода. Раньше «на запрещённом адресе ничего не происходит» нельзя было ни измерить, ни защитить от регрессии.
- **Последствия:**
  - Хелпер динамического импорта Vite вынесен в отдельный чанк `vite-helper` (`vite.config.ts`): Rollup складывал его в `sqlite-vendor`, из-за чего entry снова статически тянул весь SQLite-стек. `manualChunks` переведён в функцию, группы вендоров сохранены.
  - Что гарантируется: на неразрешённом hostname не исполняется код приложения и не регистрируется service worker; app-чанк не запрашивается, потому что статически недостижим из entry и не объявлен в `modulepreload`.
  - Границы гарантии: уже установленный ранее service worker продолжает существовать на этом origin — его `install`, `activate` и `fetch` это код, уже находящийся в браузере, и он может отвечать из кэша и выполнять свои same-origin запросы; браузер сам по спецификации проверяет обновление `sw.js`; и worker, установленный сборкой до этого изменения, может отдать старый entry без раннего гейта до первого обновления. Поэтому перед первой тестовой записью на новом адресе нужно убедиться, что на нём нет worker от старой сборки; в 4.3 это обеспечивается тем, что тестовый стенд — новый origin. Гарантия «нет никаких сетевых действий вообще» не заявляется.
  - Что проверяется у service worker на артефакте: отсутствие абсолютных внешних адресов, сохранение проверки origin запроса, отсутствие `version.json` в кэше оболочки и наличие всех файлов `assets/` в списке предзагрузки.
  - Импорты раннего входа зафиксированы разрешающим списком, поэтому новая зависимость входа требует осознанного решения, а не проходит незаметно.
