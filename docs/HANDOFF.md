## 1. Что такое IronLog

Приложение сохраняет ход тренировки и показывает точное время отдыха, даже если
экран был выключен или приложение временно работало в фоне.

- Платформы: PWA и Android через Capacitor.
- **Приложение полностью локальное.** Аккаунта, авторизации, сессий и облачной
  синхронизации нет; Supabase и его зависимости удалены. Локальная SQLite —
  единственный источник данных, резервное копирование — экспорт и импорт JSON.
  Работа без сети — основной сценарий, а не режим деградации.
- Рабочая (production) PWA: https://tmksdm.github.io/IronLog/, версия 0.26.11.
  Обновляется сама: новый service worker активируется и перезагружает окна.
- Тестовый стенд: отдельная GitHub-организация и отдельный browser origin, чтобы
  проверять сборки, не касаясь production.

- **Владелец** принимает продуктовые решения, утверждает каждый маленький шаг и
  выполняет ручные проверки (браузер, телефон), а также публикацию.

  отрицательных экспериментов. Не трогает `main`, теги, production; не публикует;

- **ChatGPT** — независимый архитектор и ревьюер: изучает diff, прогоны CI и
  отчёты, формулирует замечания. Код не пишет и не пушит.
- Никаких автоматических переходов: после каждого шага агент останавливается.

## 4. Что сделано: продуктовая переработка

Четыре задачи, принятые независимым ревью; каждая — отдельный коммит в `develop`.

- **Удалены Supabase и авторизация** (`6b0c222`). Удалены вход, гейт авторизации
  в `App.tsx`, выход из аккаунта, панель диагностики синхронизации, клиент
  Supabase, модуль синхронизации, политика облачного восстановления, очередь
  `cloud_delete_queue` (включая таблицу в схеме) и зависимость
  `@supabase/supabase-js`. Репозитории пишут только в SQLite. Из сборки и CI
  убрана вся обвязка облачных заглушек (подстановка модулей, проверка утечки
  credentials, анализатор поверхности клиента Supabase); проверка артефактов
  сохранила тестовую идентичность, CSP, префикс кэша и проверки статического
  замыкания entry, а её самопроверка теперь ломает CSP вместо подстановки
  credential. Режим тестовой сборки, host gate и `TEST_HOSTNAME` оставлены: это
  инфраструктура стенда, а не облако. Существующие базы сохранят неиспользуемую
  таблицу `cloud_delete_queue`; данные не удалялись.
- **Исправлена прогрессия упражнений без дополнительного веса** (`c2dc7db`).
  Раньше потолок `maxRepsPerSet` применялся и к ним, поэтому цель навсегда
  застревала на 8/8/8 (например, гиперэкстензия). Потолок стал необязательным, и
  для упражнений без веса цель растёт по повторам. Весовые упражнения сохранили
  утверждённое правило: 8/8/8 → повышение рабочего веса, затем снова с верха
  диапазона.
- **Исправлен откат программы бега** (`3de200a`). Равномерное состояние
  достижимо из двух разных состояний, поэтому при удалении последней записи
  восстанавливался неверный план. Теперь состояние помнит, из какого оно
  получено, и откат использует эту запись; прежняя логика осталась запасной для
  старых сохранений. Проверены требуемые переходы, продвижение по целым
  скоростям без потолка и обратимость всех достижимых состояний.
- **Расширен импорт/экспорт JSON** (`f7438cd`). Формат v2 сохраняет историю
  тренировок, упражнений, подходов, кардио и подтягиваний, а также состояния
  программ бега и турника из `localStorage`; файлы без этих полей (v1 и старый
  v2) не сбрасывают локальный прогресс. Восстановление идёт одной транзакцией
  SQLite: сбой откатывает всё. Облачный push после импорта убран.
- Проверки на `6b0c222`: линтер чистый, 149 тестов в 15 файлах, четыре сборки
  (`build`, `build:ghpages`, `build:test`, `build:android`) с проверкой артефактов
  и отрицательными самопроверками, аудит production-зависимостей — 0 уязвимостей,
  полный аудит совпал с известным списком. CI `39027718629` — success.

## 6. Путь к пользовательским испытаниям

1. **Обновить `test-deploy`** до текущего `develop` (слиянием, без force-push) и
   убедиться, что CI ветки зелёный.
2. **Подготовить обновляемую тестовую PWA**: стенд должен обновляться сам, а не
   требовать ручной перезагрузки. Это упирается в нереализованный `buildId`
   (раздел 7) — он обязателен перед первой публикацией стенда.
3. **Опубликовать тестовую сборку** только вручную и только с разрешения
   владельца — через `workflow_dispatch` и обязательное одобрение окружения
   `github-pages`.
4. **Восстановить JSON** на тестовом origin: перенести реальные данные владельца
   через экспорт/импорт, убедиться, что история, прогрессия программ и статистика
   совпадают с текущим приложением.
5. **Проверить работу на телефоне**: тренировка, отдых в фоне, турник, скакалка,
   бег, статистика, восстановление после перезапуска.

## 7. Открытые вопросы и замечания ревью

- **Проверка внешних ключей при импорте отключается.** Восстановление выполняет
  `PRAGMA foreign_keys = OFF` вне транзакции, чтобы принимать старые и неполные
  бэкапы. Плата за это — повреждённый файл может внести «осиротевшие» строки,
  которые не связаны ни с одной тренировкой. Решение сознательное; при
  необходимости отдельным шагом можно добавить проверку целостности после импорта.
- **Сохранение не является единой атомарной транзакцией между хранилищами.**
  Импорт атомарен на уровне SQLite, но дальше последовательно идут
  `saveToStore()` (снимок в IndexedDB для веб-платформы) и запись состояний
  программ в `localStorage`. Падение между этими шагами может оставить части
  слегка рассогласованными (например, восстановленная история со старой
  программой бега). Отдельного большого рефакторинга под это не начинаем.
- **`buildId` не реализован** — блокирующее условие перед первой публикацией
  стенда: без него имя кэша service worker привязано к версии, и повторные
  публикации одной версии не доезжают до установленной PWA автоматически.
- **Эмпирическая проверка ручного одобрения не выполнена.** Окружение
  `github-pages` стенда настроено (обязательный ревьювер `tmksdm`,
  `prevent_self_review = false`, `can_admins_bypass = false`, политика ветвей
  только `main`), но поведение гейта не проверено экспериментом. Проверка
  запланирована отдельным этапом с временным окружением `probe`.
- **Workflow стенда не реализован.** Логика `validate → build → deploy → verify →
  journal`, хранение проверенных сборок как release-ассетов, откат по
  `buildId` + `digest` и журнал публикаций спроектированы, но не написаны.
- **Проверка append-only семантики журнала не реализована.** Требование
  зафиксировано в README стенда и в README ветки `journal`; правила ветки
  запрещают удаление и non-fast-forward, но не порчу содержимого файла.
- **Открытый вопрос `.nojekyll`**: проверка артефакта требует его в тестовой
  сборке, тогда как опубликованный набор не обязан отдавать этот файл по HTTP.
- **Документация.** `docs/PROJECT_STATE.md` и `docs/DECISIONS.md` описывают
  состояние до удаления облака; целиком они не переписывались. `AGENTS.md`
  обновлён: правила про Supabase и `cloud_delete_queue` заменены на локальную
  модель с резервированием через JSON.
- **Проверено только автоматически.** Живой прогон приложения в браузере и на
  устройстве в рамках реализации не выполнялся — это и есть предмет испытаний.
