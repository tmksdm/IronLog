## 1. Что такое IronLog

Приложение сохраняет ход тренировки и показывает точное время отдыха, даже если
экран был выключен или приложение временно работало в фоне.

- Платформы: PWA и Android через Capacitor.
- Локальная SQLite — источник истины, облако (Supabase) — фоновый резервный
  бэкап. Сбой сети или отсутствие VPN не блокируют локальное сохранение.
- Облако не участвует в механизме обновления приложения.
- Рабочая (production) PWA: https://tmksdm.github.io/IronLog/, версия 0.26.11.
  Обновляется сама: новый service worker активируется и перезагружает окна.
- Целевое направление продукта: локальная PWA без регистрации и без облачной
  синхронизации. Пока Supabase из production не удаляется и облачные данные не
  удаляются — сначала резервная копия, сверка и безопасная миграция.
- Тестовый стенд (в подготовке): отдельная GitHub-организация и отдельный
  browser origin, чтобы проверять сборки, не касаясь production и облака.

## 2. Роли и порядок работы

- **Владелец** принимает продуктовые решения, утверждает каждый маленький шаг и
  выполняет ручные проверки (браузер, телефон).
- **ZCode (агент)** реализует только утверждённые шаги в `develop`, прогоняет
  обязательные проверки, отчитывается SHA, списком файлов, результатами тестов и
  отрицательных экспериментов. Не трогает `main`, теги, production; не публикует;
  не переходит к следующему шагу сам.
- **ChatGPT** — независимый архитектор и ревьюер: изучает diff, прогоны CI и
  отчёты, формулирует замечания. Код не пишет и не пушит. Следующий шаг
  начинается только после его ревью и разрешения владельца.
- Никаких автоматических переходов: после каждого шага агент останавливается.

## 6. Утверждённая архитектура стенда

- Публикация: ветка `test-deploy` в публичном `tmksdm/IronLog`, без форка и
  зеркала, только вручную (`workflow_dispatch`), никогда по push.
- Отдельный origin: `ironlog-test.github.io`. `TEST_HOSTNAME` заполняется только
  на `test-deploy`; в `develop` и `main` остаётся пустым, то есть fail-closed
  поведение сохраняется в основной линии.
- Workflow живёт в тестовом репозитории и состоит из заданий validate → build →
  deploy → verify → journal. Сверху `permissions: {}`, у каждого задания минимум
  прав, `contents: write` только у журнала, `pages: write` и `id-token: write`
  только у развёртывания. Секретов нет вообще. Развёртывание идёт через
  environment `github-pages` с обязательным ревьювером, то есть публикация всегда
  ручная.
- Допуск source SHA: вход — только 40 hex; checkout с `fetch-depth: 0`;
  принадлежность ветке доказывается `git merge-base --is-ancestor` (в отличие от
  `git ls-remote`, который показывает лишь вершину); допускается либо вершина
  `test-deploy`, либо SHA из журнала как откат. Необязательный третий слой —
  метка `test-verified/<sha>`, которую ставит CI источника, проверяется анонимно
  через `git ls-remote --tags`.
- Откат — **без пересборки**, на сохранённые байты: проверенные сборки хранятся
  как release-ассеты и опознаются парой `buildId` + `digest`; `digest` —
  авторитетная идентичность опубликованного содержимого, deployment ID — только
  след. Неудачная публикация продолжается запуском с `resume_build_id`: ассет
  скачивается, digest сверяется с заметками релиза, разворачиваются те же байты.
- Причина именно такого отката измерена: `version.json` содержит
  `timestamp: Date.now()`, поэтому пересборка того же SHA не даёт идентичных байтов.
- Идентификатор сборки: **архитектурно утверждён, но ещё не реализован.**
  `buildId` = короткий source SHA + номер запуска + попытка, известен **до**
  сборки; в тестовом режиме попадает в имя кэша service worker и в `version.json`;
  digest считается после формирования всех файлов, поэтому цикла нет. Реализация
  обязана быть завершена и проверена **до первой публикации тестового стенда**.
  Самостоятельно реализовывать его сейчас запрещено — нужен отдельный
  утверждённый шаг.
- Журнал: отдельная ветка `journal` с rulesets, которые запрещают удаление и
  force-push, но без bypass-акторов — обычный append push проходит. `published.json`
  append-only, ключ — `buildId` + `digest`. Параллельные запуски исключены через
  `concurrency` с `cancel-in-progress: false`; конфликт — повтор с `pull --rebase`,
  затем явный отказ. Журнал не единственное доказательство допустимости отката:
  независимо существуют релизы (байты и digest), история развёртываний Pages и
  запуски workflow.
- Проверка по HTTP: главное доказательство — SHA-256 фактически полученного
  содержимого каждого файла из манифеста. Файлы, начинающиеся с точки (включая
  `.nojekyll`), из обязательного сравнения исключены; `Content-Length` как
  доказательство не используется. Кэш отключается, но полагаться на это нельзя,
  поэтому сначала ворота свежести: `buildId` в отданном `version.json` обязан
  совпасть, и только затем сравниваются файлы. Дополнительно сверяются ссылки из
  `index.html`, список `PRECACHE_URLS` из отданного `sw.js`, чанки из графа
  модулей, запускается `check-artifacts.mjs --mode test` по скачанным файлам, и
  отсутствующий путь обязан вернуть 404. При этом существующая проверка
  `check-artifacts.mjs` требует наличия `.nojekyll` в тестовом артефакте —
  расхождение с опубликованным набором зафиксировано как открытый вопрос в
  разделе 8.
- Ограничения безопасности: только бесплатные сервисы, никаких дополнительных
  аккаунтов, форков и зеркал, никакой автоматической публикации. Тестовая сборка
  без облака (заглушки плюс CSP `connect-src 'self'`) и без credentials.
  Production остаётся на `tmksdm.github.io` и не затрагивается.

## 8. Открытые задачи, риски, ближайшая контрольная точка
